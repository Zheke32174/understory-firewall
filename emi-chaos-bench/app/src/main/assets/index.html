Main-thread—
The sound-and-app stutter that happened when the BLE chaotic cadence ran with Bluetooth switched off — isolated, rebuilt as its own function, and now identical whether Bluetooth is on or off.

What was actually causing it: EMIBridge.bleScan() is a synchronous JavaScript-to-native bridge call, and the audio engine is a ScriptProcessorNode — which also runs on the main thread. With Bluetooth off that native call returns instantly (the LE scanner is null), so the cadence fired far more often and hammered the main thread with bridge round-trips and DOM writes. Those collide with the audio callback's real-time window and cause buffer underruns: the stutter. With Bluetooth on, Android's scan limiter slowed the cadence, the collisions became rare, and it vanished.

How it hits. The bar above is the anvil — every cell is a real laid-out element. Each burst writes geometry to those cells and immediately reads geometry back, interleaved, which is the one pattern the browser cannot batch away: it must lay the page out synchronously, on the main thread, in the window the audio callback needs. Reads rotate across offsetWidth, offsetHeight, getBoundingClientRect(), clientHeight and getComputedStyle(), and a class is flipped on the container between passes so style is invalidated for the whole subtree rather than a single node. Synchronous native bridge round-trips — the original cause — run in the same burst.

Maximum capacity is measured, not guessed. A burst does not run a fixed number of operations; it runs until its millisecond budget is spent. A faster phone therefore does proportionally more work in the same window, and the hammer always fills whatever the device can actually deliver. Ops/burst is what your device managed. The scheduler then divides the measured burst cost by a target duty cycle to set the next gap, so it self-tunes to a known share of the main thread rather than a guessed interval. Main-thread is that share. Overdrive raises the ceiling to roughly 70%.

The audible glitch (short holds and drops — exactly what a stalled or dropped buffer sounds like) is also asserted directly in the audio path, so the effect is reliable rather than dependent on how fast a given phone's bridge happens to be. The duty-cycle cap is what keeps this a deliberate effect instead of an ANR: the main thread keeps a guaranteed share at every severity, overdrive included.

Last trip—
Watches the masker's own recent output for signs it's settling into a too-regular, more easily filtered-out pattern. If it holds steady for a few checks in a row, this fires an unprompted remodulation burst — reseeds every chaos core, hard-rerolls half the dials, spikes the mash rate briefly — to keep the output from ever sitting still long enough to be learned. Two independent views now run: the pattern score is what a coherent/FM-style recovery sees (waveform autocorrelation), and the AM envelope score is what a plain envelope detector sees — rectify, low-pass, read whatever rhythm is left. Those fail differently: a chaotic waveform whose loudness still breathes on a schedule is trivially AM-strippable, so an AM trip fires a different burst that rerolls the level/drift dials shaping the envelope, not just the carrier. AM depth is the modulation index — a deep and periodic envelope is the genuinely demodulable combination; shallow or chaotic is fine.
Spectrum band guards—
Start the masker to begin band analysis.
Nine independent demodulation guards, infrasound through ultrasound, each with its own waveform and envelope score and its own band-targeted correction. The global guard above asks "is the whole output predictable?" — these ask it per band, because a band-limited listener filters to the slice they care about first, so one tidy band is all they need.

Infrasound (<20Hz) can't be seen in the 43ms capture window at all — one 10Hz cycle is 4800 samples — so that guard runs off a separate decimated envelope buffer spanning ~5.5s, resolving to about 0.4Hz. It's asking whether the loudness pulses at an infrasonic rate, which is the demodulable thing at those frequencies. Ultrasonic (>18kHz) normally reads quiet on a phone speaker; that's expected physics, not a fault. Bands below an energy floor report quiet rather than a score, because normalised autocorrelation on a near-empty band divides noise by noise and returns confident nonsense.

The radio-free chaotic timing engine, extracted from an observation that the BLE chaotic cadence behaves better with Bluetooth switched off.

Why that happens: with Bluetooth off, Android returns a null LE scanner, so the native scan call returns instantly having touched nothing — and the cadence therefore runs completely unthrottled, firing exactly when the chaos maths says. With Bluetooth on, Android's BLE scan limiter (~5 starts per 30s per app) silently clamps it, handing back a slower and more regular pattern than was asked for — the same invisible-throttle problem as the Wi-Fi scan budget.

So the good part was never the Bluetooth activity; it was the pure timing chaos, which the radio was only ever getting in the way of. This is that, standalone: no radio dependency at all, free to run far faster than any scan API permits, and running simultaneously with real BLE scanning rather than instead of it — so having Bluetooth on no longer costs you it. At maximum magnitude it reaches roughly a thousand times the effective rate the throttled BLE-backed version could sustain. Each pulse injects entropy where it changes the output: reseeding chaos cores, perturbing mash dials, driving the sensor bus.

Drives brightness, colour temperature, saturation and a slight hue drift off the same chaos cores as the audio. Every axis is clamped to a deliberately conservative window — brightness only ever dims to 72% of your own setting and never brightens past it, saturation stays within ±10%, hue within ±6° — and all of it is slew-limited.

The chaotic-cadence idea applied to every remaining sensor: on each burst it hammers a randomized subset of the native reads — GNSS satellite status, cell info, thermals, the raw sensor snapshot, the LAN ARP table, the cell guard — a randomized number of times, in randomized order, then goes quiet for a randomized interval (same sprint/long/marathon/lurk modes as the radios). Looks for someone escalating against this app — code injected into its address space, a tracer attached to its process, the sandbox not being enforced, or a payload running from memory with no file on disk.

This is not a root blocker. It does not care whether you have rooted your own phone, and it will not refuse to run if you have — that punishes the owner for controlling their device and stops no attacker. The question here is the opposite one: has anything got inside this app.

What it checks: TracerPid for a live ptrace attachment (the mechanism a debugger or injector uses to read and write this app’s memory); memory mapped both writable and executable, which normal code never needs; executable regions backed by memfd or deleted files — code never written to disk, which is what an obfuscated in-memory implant looks like and what a file scanner can never find; native libraries loaded from world-writable or shell-owned directories; known code-injection frameworks mapped into this process; whether SELinux is enforcing; whether this app’s own APK sits where it should and is read-only; and overlay mounts covering system paths, which is how a rootkit shows one filesystem to some processes and a different one to others.

It reports and never blocks. No self-kill, no lockout, no “integrity failed”. Retaliation is trivially bypassed by anyone who has already achieved injection, and a false positive would end a masking session you may be relying on. A finding costs you a notification and a line in the encrypted log — that is the entire response, deliberately.

Honest limit: an attacker with kernel-level control can defeat every check above — they can lie about /proc, hide mappings and forge the answers. This raises the cost of a quiet compromise; it cannot prove there isn’t one. Several checks also have legitimate causes (the ART JIT produces some writable-executable pages; some ROMs overlay system paths), so findings state what was observed rather than declaring a verdict. Runs natively on a slow cadence in the background, so a tracer attaching while the app is out of sight is still caught.

No injection or hijack signatures yet.
Two layers of the same question: is what this app reads actually what the hardware and the runtime produced?

Sensor injection. MEMS gyros and accelerometers have mechanical resonances — sound at roughly 19–20kHz can couple into the sensing mass and show up as motion that never happened (Son et al., Rocking Drones with Intentional Sound Noise; Trippel et al., WALNUT). Three signatures separate that from real movement: the stream going narrowband (driven by a tone rather than messy human motion), gyro and accelerometer disagreeing about whether the phone is moving at all, and repeated identical samples indicating a replayed or clamped feed. They're fused, never used alone — a phone on a vibrating surface trips the first, a phone flat on a desk trips the second, so it takes two signatures (or one plus corroborating ultrasonic mic energy) to report.

Runtime hijack. If something injected JS into this page or swapped the native bridge, every other readout here becomes whatever the attacker wants. So the primitives this engine depends on and the bridge methods themselves are snapshotted at load and re-checked for still being native code. Anything that stops being native has been replaced.

Everything here reports and nothing blocks. A false positive should cost you a notification, never your masking session.

Privileged access tiers—
Native build only.
—
Four tiers, and they are not interchangeable — saying "Dhizuku as a Shizuku fallback" would be half a lie, so here's the real split:

Shizuku runs as the adb-shell UID, which is the only tier that can serve the read-only dumpsys diagnostics. Dhizuku is backed by device owner, and its process API spawns inside a normal app UID — so shell output through it comes back no more privileged than ours, and it cannot replace the diagnostics if Shizuku goes away. Nothing can; that capability simply leaves with Shizuku.

What Dhizuku and device owner provide instead is something Shizuku genuinely can't: setUserControlDisabledPackages (Android 11+), the one supported mechanism on stock Android that makes an app resistant to being silently force-stopped. That's the real answer to "can't be tampered with without appops" — once set, stopping or uninstalling the masker takes a deliberate privileged action rather than a background tap. Device admin alone is weaker: it greys out the Settings buttons, but adb can still stop the app.

Force-stop protection goes through Dhizuku first. Dhizuku is itself the device owner and delegates policy to this app, so the protection works without making this app the device owner — which is deliberately not recommended and is not the path any button here takes. Self-provisioning device owner is a one-shot step that requires a device with no accounts added and a factory reset to undo; that is a wildly disproportionate thing to do for a masking app, so it is listed for completeness only.

Every tier is optional and the app works without all of them. The declared device-admin policy set is deliberately minimal — no wipe, no password control, no login monitoring.

The list above is the in-page view and is capped. The vault is the real record: encrypted with a non-exportable Keystore key, append-only, and hash-chained so a removed or edited entry is detectable rather than silent. There is deliberately no delete or clear anywhere on its interface.

Each entry now carries the device context at the moment it was recorded — battery level and whether it was charging and on what, battery temperature, whether the screen was on, dozing or in power-save, network type, whether the masker was actually running, process uptime, app version and device model. A finding without its situation cannot answer the questions that decide whether it mattered: was the phone idle and face-down, or in use? was this a live observation or the idle baseline? was the device hot enough for the sensors to be drifting? It also makes patterns visible across entries — "all of these happened while charging, screen off" is a pattern; a list of timestamps is not.

The context is sealed inside the same record as the message, so it is covered by the same authentication tag and hash chain — context that could be altered afterwards would be worse than none. It deliberately carries no location, SSID, BSSID, cell identity or device serial: this is exactly the file most worth stealing, and a precise location history would be the most damaging thing in it. Network type is recorded; which network is not.

Export writes the full detail — every record, the context, the chain fields, and the result of verifying the chain, embedded in the export itself. An exported log that does not state whether its own chain verified is a document the recipient cannot trust. CSV flattens the context into columns for a spreadsheet; JSON keeps everything. If a record cannot be authenticated, the export says exactly where reading stopped instead of quietly returning a shorter file.

The attack: another app draws a window on top of this one and leaves it transparent, or leaves a hole in it. You believe you are tapping a control here; the touch actually lands on the attacker's window, or their window is lying to you about what the control underneath does. It is how permission dialogs and confirmations get subverted on Android, and it needs no root — only the overlay permission, which many ordinary-looking apps request.

The defence, and it is real: Android flags every touch delivered while another window covers this one. filterTouchesWhenObscured makes the framework discard those touches before they reach anything. This is the one place in the whole app where something is genuinely blocked instead of reported — a tap you did not knowingly aim here should not land, and the cost of dropping it is that you tap again. Blocked taps counts them, so an attack that gets defeated is visible rather than silent.

Accessibility services can read the content of every screen and inject gestures — the most powerful thing an app on Android can hold, and the usual home of stalkerware. Enabled ones are listed so an unexpected entry is obvious, with a button straight to the settings screen that turns it off. This app does not request an accessibility service for itself: the capability it would grant is exactly the capability this app exists to warn you about, and holding it would make this the most dangerous app on your device.

Holding the overlay permission is not itself wrongdoing — screen recorders, chat bubbles and colour filters all use it legitimately — so the list is shown without accusation. The blocked-tap count is the signal that matters.

The detector for what cSploit and Intercepter-NG do. Those tools ARP-poison a network to become the gateway and then read or rewrite everyone else's traffic. None of that is built here and none of it will be — but the same knowledge pointed the other way is exactly what a counter-surveillance tool should carry.

How it looks from the victim's side. The attacker tells your phone "the gateway is at my MAC address" and your kernel believes it. So the signature sits in a table this device already keeps for its own reasons: one MAC answering for several IPs (a poisoner impersonating the gateway ends up bound to multiple addresses), and the gateway's MAC changing while you stay on the same network — the moment of the takeover. Both have innocent explanations: a router that is also DNS and DHCP, or a mesh handing you to another access point. They are reported with their addresses rather than asserted as attacks.

Everything here is a read. /proc/net/arp is the kernel's own table, populated by traffic this device was already part of — the same category as ip neigh. No ARP is sent, no packet injected, no host probed, no other device's traffic touched. That distinction is the whole point: the attack tools transmit, this does not.

Resolver and tunnel posture come from LinkProperties — local state the OS already holds. This deliberately does not probe a remote resolver or fetch a canary URL to test for DPI: that would mean this app generating traffic of its own, which is a posture it does not have and should not gain quietly. If ARP is unreadable (Android 10+ restricts it on many builds) it says so, rather than reporting a clean network it never actually looked at.

Interception posture, without probing. RKNHardering answers "is my traffic being blocked, redirected or inspected" by reaching out and testing. Doing that here would mean this app generating its own outbound traffic — a counter-surveillance tool that phones out is a contradiction. The redesign: Android already probes. The platform validates every network it joins and stores the verdict, so reading it costs nothing and sends nothing.
· Captive portal — the network is intercepting and redirecting traffic. Normal for hotel and public Wi-Fi, and also exactly the position an attacker needs: everything passes through equipment that has already shown it will rewrite your traffic.
· Not validated — traffic is not reaching the internet as expected. A dead connection looks like this; so does one where something is interfering with the check.
· System HTTP proxy — all proxied traffic is terminated by someone else's server, which can read and alter anything not end-to-end encrypted. A configuration rather than an intrusion, but if you did not set it, something else did.
· Private DNS — with it off, lookups leave in plaintext and whoever runs the network sees every name you resolve and can answer with whatever they like.

Ports the parts of PrivacyCell, AIMSICD and SnoopSnitch that work without root, and is explicit about the parts that do not.

Connection security (PrivacyCell, ported in full — it needs only READ_PHONE_STATE). 2G is the one that matters: GSM encryption is A5/1, broken in practice, or A5/0, which is none at all — and 2G never authenticates the network to the handset, so your phone cannot tell a real tower from a fake one. Being pushed onto 2G is the classic interception setup.

Rootless catcher heuristics (AIMSICD's cell-list detections):
· Generation downgrade — being dropped from 4G/5G to 2G/3G on the same carrier is how an interception device gets a handset onto equipment it controls.
· No neighbouring cells — real macro cells advertise neighbours so the phone can hand over; a cell with none may have no network behind it.
· Serving cell dominance — handsets pick the loudest tower, so a device trying to capture phones has to out-shout the real network.
· Area-code flip — the tracking area changing while the cell identity stays the same is not something a real cell does.

What root would add, and why this is a lesser form. SnoopSnitch reads the Qualcomm DIAG interface to see the baseband message flow directly — the cipher actually negotiated, silent SMS, IMSI paging. That needs root, a Qualcomm chipset and a diag-capable ROM, and there is no rootless substitute: no public Android API exposes the negotiated cipher. So this reports what the generation can offer, not what your baseband actually agreed to, and says so rather than implying a confidence it cannot have.

Every check is a heuristic. Rural cells genuinely have no neighbours, tracking-area boundaries genuinely flip while you stand still, femtocells and repeaters genuinely out-signal macro cells, and 2G fallback genuinely happens where there is nothing else. A flag is a reason to look, never a conclusion.

Nothing is switched automatically. No band forcing, no RAT locking, no radio reconfiguration — dropping a phone off 2G at the wrong moment can cost an emergency call, which is a worse outcome than being surveilled. It reports; you decide.

Detects a BLE tracker that is travelling with you — the analysis runs natively and commits straight to the encrypted log, so the page cannot alter a verdict or suppress a finding, and the history survives a reload.

Why a single scan can never answer this. A tracker in your bag and a tracker on a shelf you walked past look identical in one sweep. They differ over time: the one travelling with you keeps being seen, across places far enough apart that a fixed beacon could not reach both. So a follow requires both — persistence across several separate scan sessions and real displacement since it was first seen. A beacon reaches tens of metres; if the same identity is still with you half a kilometre later, it moved with you.

MAC rotation is handled. Trackers rotate their hardware address to defeat simple blocklists, but the advertisement payload usually stays constant — so identities are keyed on the payload, and the same payload appearing under several addresses is itself reported. Vendor fingerprints (Apple Find My, Samsung SmartTag, Tile, Chipolo) are read from manufacturer data.

Deliberately conservative, and it will name your own things. Your AirTag, your earbuds, a tag belonging to someone travelling with you, and a tag in a shared car all produce a genuine follow signature — because they genuinely are following you. The alert says exactly that rather than implying malice. Identify it before assuming the worst.

It now observes without this screen. The scan is owned by the foreground service, not by this page, so a tracker planted in a bag is followed with the phone in a pocket and the display off — which is the only state in which a planted tracker actually gets followed for hours. One continuous low-power scan is harvested into 20-second windows rather than restarting on a cadence: Android silently drops scan starts past roughly five per thirty seconds, so one long scan sees more than an eager one, and steady observation is what this particular detection wants anyway.

Native scanner above says whether it is genuinely observing. A follower panel reading "nothing following" while nothing is scanning would be indistinguishable from an all-clear, so Bluetooth being off — an ordinary state, not an error — is named rather than hidden.

Tower Collector and GPSLogger, ported — both are rootless already, so this is a port rather than a lesser form. Records which cell you were attached to, where, and how strongly, on GPSLogger's interval + distance triggers with an accuracy gate that throws away fixes too vague to be worth keeping.

Why it belongs here rather than beside the live cellular checks. Those work on what is visible right now — one sample, no memory. Half of what makes an interception device visible only exists across time and space: a cell that appears in one place and never again, an identity that shows up at two locations kilometres apart, a tower present for twenty minutes and then gone. None of that is detectable from a single reading. This is the record that makes those questions answerable, and it flags the same cell identity seen at an impossible distance from where it was first logged — a fixed tower cannot be in two places. This log contains location, unavoidably — a position log without positions is nothing. That is exactly why it is kept out of the encrypted alert vault, which is deliberately location-free: the vault is the file most worth stealing, and mixing a movement history into it would destroy that property. This is a separate store you export deliberately, and it is the one part of the app to treat as sensitive on its own terms.

Nothing is uploaded. Tower Collector's OpenCelliD submission is deliberately not ported — an app that quietly uploads a counter-surveillance user's movements would be self-defeating. Runs on the service, so it keeps logging with the app backgrounded, which is when you are actually moving past towers.
